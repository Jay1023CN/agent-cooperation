# 模型分配、记忆与代码交接

## 任务如何选择成员

每个配置项代表一位实际可运行的成员：客户端、模型、所在电脑、允许角色、任务能力以及并发限制。GLM 等模型必须放在能运行它的客户端配置中；仅填写模型名称不会获得新的模型权限。

派发先检查硬条件：电脑最近在线、成员空闲、机器并发有余量、角色和任务能力匹配、本机接入检查通过。指定成员也必须满足这些条件。验收者不能是原执行成员。已声明额度耗尽或处于暂停期的成员不会领取任务；难度超过承接范围或已知上下文容量不足的成员也被排除。

然后对所有在线电脑的候选成员评分，因此不是哪台电脑先轮询就抢到任务。项目可选均衡、质量优先或节省额度策略，并设置优先客户端。难任务、负责人和验收任务增加质量权重；常规任务增加速度和经济性权重。最近至多 12 个执行结果在至少有 3 个样本后才参与有限幅度的排序，不视作模型能力的权威评测。

每次领取把选择原因保存在任务中，包括任务难度、策略、模型、偏好匹配与可用历史。没有候选时任务保持排队，页面显示已注册成员的实际接入状态。正在执行的任务不会因为偏好变化被换模型或重跑。

以下字段是你们根据实际体验填写的声明，不是自动读取的订阅价格或剩余 token：

```json
{
  "model": "该客户端支持的模型 ID",
  "routing_profile": {
    "quality": 4,
    "speed": 3,
    "economy": 5,
    "max_difficulty": "deep",
    "context_window": 128000,
    "quota_state": "unknown",
    "paused_until": 0,
    "preferred_for": ["code", "debug"]
  }
}
```

质量、速度、经济性各为 1–5；额度状态为 `unknown`、`available`、`limited` 或 `exhausted`。`paused_until` 是 Unix 时间戳。任务难度为 `routine`、`standard`、`deep`，`context_tokens` 是预计需要的上下文规模。未知容量或额度在原因中明确标为未知，最终模型权限与额度由客户端决定。原有 `preference` 数字越小越优先，作为评分中的小幅偏好保留。

电脑安装了桌面软件、连接协议可用、账号已登录以及模型有剩余额度，是不同的事实。本机检查只报告它能验证的部分。用 `pal-arena doctor --config worker.json --json` 查看诊断，不会发送模型任务。

## 记忆如何进入任务

项目记忆供团队共享，个人偏好只进入该成员的个人会话。共享任务不会收到个人记忆。需求清单和当前任务要求优先于记忆；项目共同约定优先于与其冲突的个人偏好。

负责人处理成员对话时，会直接整理长期有用的偏好、背景、决策和约束，无需逐条手动确认。成员可以在记忆页查看、修改、停用或删除；其他执行成员提出的建议仍作为候选。每次修改都有版本号，同时修改同一条时会要求刷新。

是否值得记由负责人模型根据对话判断：它会从用户的选择、表扬、反感和纠正中主动识别偏好，也会记录后续工作要沿用的项目决定。用户不需要说“记住”或“以后都这样”；反复出现的反馈可以帮助判断，但不是保存的前提。模型会结合上下文区分临时要求与可能适用于类似任务的偏好，标明适用范围；缺乏依据的推测和凭据不记录。内容改变时优先更新已有记忆，完全相同的记录去重。模型的判断可能遗漏或误记，成员可以随时更正。这里没有独立的记忆评分模型，也不需要额外配置模型 API。

任务每次领取时保存一份已启用记忆快照，含记忆 ID、来源任务和版本。默认只选取最多 24 条、总共 24,000 个字符的内容，优先项目规则、约束与偏好。任务详情中的快照是本次实际使用的集合。新增或修改记忆不会悄悄改变正在执行的上下文；任务明确调用 `memories(refresh=true)` 才更新本次快照，并记录刷新事件。重试作为新的一次执行会读取最新启用版本。

快照以外的旧记忆可以通过 `search_memories` 按主题检索，搜索只涉及当前任务有权读取的范围。负责人发现同一范围里的记忆重复时，可以通过 `consolidate_memories` 将相关内容压缩为一条，保留适用场景和重要差异；原条目变为“已合并”，仍能在记忆页查看或重新启用。整理发生在负责人处理对话时，不依赖定时任务或额外模型服务。搜索使用本地关键词匹配，并非向量语义搜索。

聊天记录、任务证据和长期记忆分别保存。无需把所有聊天都复制到长期记忆中，也不能靠记忆改变已验收提交或需求版本。

设计参考：[Codex 的单次会话提取](https://github.com/openai/codex/blob/main/codex-rs/memories/write/templates/memories/stage_one_system.md)、[Codex 的记忆整合](https://github.com/openai/codex/blob/main/codex-rs/memories/write/templates/memories/consolidation.md)和 [Deep Agents 的记忆加载](https://github.com/langchain-ai/deepagents/blob/main/libs/deepagents/deepagents/middleware/memory.py)。它们的实现方式不同，本项目使用现有数据库与客户端，不直接照搬文件结构。

## 代码如何保持一致

GitHub 是跨电脑交接的来源。任务使用独立目录和 `arena/<task>/<attempt>` 分支。执行证据记录具体提交 SHA；依赖和验收读取该提交，不读取随时可能变化的分支头。Agent 自己提交的改动也纳入本次差异。工作分支推送失败时保留本地提交和失败原因，不能显示成已经同步。

依赖任务通过验收后，后续任务才能合并它的提交。出现冲突会停止当前任务，保留现场；不会强制覆盖文件。空 GitHub 仓库使用相同的确定性初始提交，让不同电脑产生的首批任务分支可以整合。非空仓库找不到所配置的基础分支时不会任意新建不相关的历史。

独立验收针对执行产物与当前需求版本。需求变化后旧验收不能直接完成交付。发布执行器整合全部当前已验收提交，再运行本地配置的集成检查，最后按项目策略执行非强制推送及部署。伙伴同时更新基础分支时，推送会拒绝覆盖，保留结果供处理。

断线、进程退出、服务恢复与任务取消，都可能发生在外部操作已经完成之后。因此未知结果不会自动重试。执行机在 `_receipts/<task>/<attempt>.json` 保存不含运行令牌的本地回执；先检查回执、GitHub 提交和实际客户端，再决定是否重试。备份恢复的排队、执行和协调任务也默认暂停，详见 [维护与恢复](arena-maintenance.md)。
