# Multica + PAL 整合方案

本文记录目标架构、已有能力与未完成工作；方案不代表已在用户设备上部署或验收。仓库的 `third_party/multica` 子模块固定上游源码版本 `8ffcc88`；该源码由上游单独维护，需要按需执行 `git submodule update --init third_party/multica` 获取。部署前仍需重新检查与所用客户端版本的兼容性。

## 目标与机器

两名成员在同一工作台讨论比赛项目，让一名负责人拆解研究、文档、网页、代码、调试和 Blender 工作，分派到四台电脑上的真实代理，再安排独立成员检查实际成果。机器为常开 Mac mini（24 GB / 512 GB）、Mac Neo、Windows 天选 6 Pro 和 Windows 天选 7 Pro Max。Mac mini 没有公网 IP；中心暂存目标为 5 GB，不把四台电脑的全部缓存和 GitHub 存储算进这项预算。

## 组件与唯一数据来源

1. **Multica 服务端与网页**：计划运行在 Mac mini，负责工作区、成员、任务、会话、运行状态和基础运行日志。以其任务和运行作为唯一来源，不让第二套任务调度器重复派发。
2. **各机 Multica daemon**：连接中心，并在本机启动与之兼容的客户端 CLI。跨电脑通信由中心与各机 daemon 完成。
3. **PAL Agent Link**：通过 MCP 补充本机桌面会话和现有客户端适配。PAL 桌面端口只在本机访问；通过 PAL 桥接时，需要一个支持 MCP 的宿主代理，其自身也可能消耗订阅额度。
4. **GitHub**：保存仓库、任务分支和提交；执行电脑各自检出。GitHub 不是运行状态数据库，也不会自动同步任意本地文件。
5. **独立 UI**：Multica 原有网页可用于基础操作；自定义界面保持独立、经稳定接口访问，遵守 Multica 界面及非界面用途的许可和署名要求。浅色/深色跟随系统，复用同一套字号、间距与组件规范。

PAL Arena 是本仓库的**独立原型**，已经实现部分分配、记忆、Git 交接和验收逻辑；它不等于 Multica 插件，也不与 Multica 自动同步。整合时逐项移植或抽出可复用能力，建立清晰的数据所有权与测试；不同时启用两套任务领取和完成流程。

## 客户端接入顺序

| 客户端 | 方案 | 当前限制 |
| --- | --- | --- |
| Qoder / Qoder CN | 优先评估 Multica 原生 CLI 运行时，也可经 PAL ACP 新建会话。 | 实际 CLI 登录、模型及订阅资格待验证。当前参考版本的 Multica 原生 Qoder 固定使用 `--yolo --acp`；PAL ACP 的权限请求则由桥接调用者处理。不能把两者权限方式视为相同，也不能假定宿主模型一定会等待人工授权。 |
| WorkBuddy 桌面版 | 目标是在已登录的桌面会话中主动领取共享任务，明确提交结果，再经独立验收。 | 现有桌面 MCP 桥仅连接 Arena；Multica 侧任务交接与状态回写尚未实现。本地助理 Open API 没有可靠的任务终态，不能把收到消息当作完成。 |
| Antigravity | 可评估 Multica `agy` CLI，或经 PAL 调用本机桌面会话。 | CLI 与桌面会话是不同路径；安装、登录、模型和会话能力需验证。 |
| Codex / Claude / Gemini | 优先评估 Multica 或 PAL 已有的对应 CLI 支持。 | CLI 与桌面订阅的登录和额度关系以各厂商及账号实际情况为准。 |
| GLM | 通过实际提供它的客户端选择模型。 | 模型名本身不能启动代理；具体支持与订阅资格待验证。 |
| Blender | 派给安装 Blender 的执行电脑，保存 `.blend`、导出文件与检查记录。 | 专用适配、版本和渲染能力尚未联调。 |

不静默切换至供应商云任务、API Key 或额外付费服务。模型额度、价格和可用上下文无法自动确认时明确标记未知。

## 用户流程

1. 双方登录并进入共享项目，写下目标、仓库、基础版本和验收清单；个人讨论和共享项目内容按权限分开。
2. 负责人基于当前需求拆出有输入、依赖、能力要求、文件范围、交付物和验收方式的子任务。Multica 小队只有一名负责人；另一名可作为评审成员。负责人必须明确指派，不能假定小队会自动广播任务。
3. 根据在线状态、角色、能力、并发、上下文、明确暂停或额度耗尽等硬条件筛选；再结合项目策略、成员偏好和有限历史表现排序，保存理由。选不到成员时保留等待原因。
4. 执行者在独立工作区和分支工作，回报机器、客户端、会话、提交、检查和产物。依赖任务引用确定提交；分支推送失败或合并冲突应如实显示。
5. 由不同成员读取需求、提交和文件，独立检查并记录证据；不把一句“完成了”当作验收。需求版本变化后需重新核验。
6. 负责人汇总可交付内容、未完成项与风险。部署、合并和正式提交遵循项目约定及成员授权。

现有 Arena 原型的分配、记忆和 Git 逻辑可供复用，但这六步在 Multica 上的完整自动闭环尚未实现。

当前 PAL MCP 已提供只读的 [模型分配建议](multica-model-routing.md)：基于调用方提供的状态快照和声明的偏好筛选、排序并解释原因。它不代替 Multica 调度，也尚未自动采集各机状态、预留名额或保存全局模型配置。

## 记忆与偏好

共享项目约定和个人偏好分别保存并执行访问控制；个人内容不能仅靠提示词防止进入共享运行。成员批准的记忆有来源、版本、停用和冲突处理；代理提出的建议先进入待确认状态。每次运行固定其实际使用的记忆快照，需求优先级高于任务，任务高于已批准记忆与偏好。需要为 Multica 设计明确的成员身份映射、存储、访问控制、版本与运行快照，不能直接宣称 Arena 的隔离已覆盖 Multica。

## 存储、网络与恢复

- 计划通过 Tailscale 等私有网络连接四机，不要求公网 IP，不把桌面代理本地端口开放到公网。成员登录、服务访问控制和加密连接需在真实网络验证。
- Multica 自托管包含服务端、网页、PostgreSQL 和各机 daemon；容器镜像、数据库、运行目录、日志及缓存都需要实测。中心 5 GB 暂存目标不是数据库、Docker 镜像或操作系统层面的硬配额。清理不得删除正在执行的任务、未同步提交和结果不明的现场。
- 当机器断线、任务取消或提交响应丢失时，检查该客户端、工作区、提交和任务记录后再恢复；不能对结果不明的写操作自动重发。Multica 上游有自己的离线重试规则，整合时必须核对并调整，不能假定已经满足此要求。
- 当前参考版本的 Multica 自托管默认启用每日部署级匿名遥测，可按其文档使用 `DO_NOT_TRACK=1` 关闭；配置时应明确记录。

### 参考版本中必须处理的上游行为

- 普通任务工作目录初始没有仓库，任务内需要使用 `multica repo checkout <url>` 请求守护进程创建检出；该操作需要运行中的任务令牌和 daemon 本地端口。桌面会话如果不持有该令牌，桥接层必须提供受限的检出交接或使用已准备好的工作区，不能凭 `cwd` 假定已有代码。参见 [工作目录准备](https://github.com/multica-ai/multica/blob/8ffcc88/server/internal/daemon/execenv/execenv.go)。
- 当前源码会对 `runtime_offline`、`runtime_recovery`、`timeout` 和部分网络故障等情况创建重试；常规默认预算为首次加一次重试，特定网络故障可到三次。即使适配器拒绝重新领取，服务端仍可能创建重试记录；接入前要核对全部触发入口，并实现禁重派或持久去重，不能只靠提示词。参见 [重试逻辑](https://github.com/multica-ai/multica/blob/8ffcc88/server/internal/service/task.go)。
- 上游 `Prepare` 在重跑某些原任务目录时会清空目录内容，另有复用已有目录且不删除的路径。状态不明、已有未同步代码或桌面客户端仍在写入时，必须先核实具体运行路径并保护工作区；不能声称上游默认满足现场保留。详见同一工作目录准备源码及 `multica repo checkout` 的保留规则。
- 可评估的 WorkBuddy 方案是本机交接桥：Multica 调用兼容的执行端后等待，已登录的 WorkBuddy 会话通过 MCP 主动领取并显式提交**候选结果**；另一个成员仍需验收。桥要有持久运行记录、身份隔离、取消/失联状态和跨进程互斥，并覆盖上面的检出、重试和目录清理行为。当前该桥尚未实现，WorkBuddy 也不会因为安装桌面客户端就自动成为 ACP 服务端。
- 本地交接记录的基础存储已实现（`agent_link/handoff_store.py`）：同一已核实的重试链在同一数据库中只允许创建一条记录，领取使用数据库事务，重启后不会自动重新领取；结果提交只是候选结果。它尚未连接 Multica 或 WorkBuddy，也不能阻止不同电脑各自领取同一重试链。调用者必须核实重试链身份，数据库需要放在仅当前用户可访问的位置，不能写入任务令牌。跨机去重、取消、授权恢复和结果回写仍需实现。

## 开发与验收顺序

1. 固定上游版本，梳理各 CLI 的权限、任务身份、状态与 MCP 契约；在本地用模拟客户端覆盖接收、审批、超时、断线和结果不明。
2. 完成 Multica 的负责人任务模板与客户端接入，避免重复控制平面；针对 WorkBuddy 设计并实现桌面端主动交接与状态回写。
3. 将路由、共享/个人记忆、Git 交接和独立验收逐项接入，覆盖权限边界、并发写入、需求变更与失败恢复。
4. 本地验证 Web 与浅色/深色主题，检查安装、自检、备份、日志和中心存储用量。用户决定部署后，再从一台电脑开始，扩到两台、四台及预期并发。
5. 实机验收包括各客户端真实订阅与模型、GitHub 交接、网络断线、独立验收及 Blender 可打开产物。真实设备不可用期间，这些项目只能标记待验收。
